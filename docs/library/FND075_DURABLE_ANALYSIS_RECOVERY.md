# FND-075 durable analysis recovery

FND-074 bounds attempts. FND-075 makes eligible completed work recoverable from durable state instead of inferring completion from a timeline or an in-memory result.

## Protocol

- A checkpoint is keyed by tenant, workspace, project, pipeline, run and stage. Its input version, lease owner, fence, attempts and output reference are durable. A claim is renewed every eight seconds during work and expires after 30 seconds without renewal. A new claim increments the fence. The current fence is validated in the SQL transaction before output can become authoritative.
- Cleanly interrupted worker work and explicitly transient failures can be recovered at most three times including the original attempt by default. Non-replayable units have one attempt. The Authority queue uses the original run admission deadline. SecureNow saves an absolute deadline with the capture. Redelivery never creates a fresh budget. Neither timeout nor permanent failure triggers an unrestricted retry.
- Queued Authority checkpoints context, graph, and findings as separate SQL transactions. A replacement worker rehydrates their actual scoped outputs. A missing output fails closed. Decisioning, artifact synthesis, manifest seals, run completion, and receipt are one transaction because the decisioning draft is not an independently durable artifact. Finalization requires all three checkpointed prerequisites and the successful final stage group. Starter task creation and its handoff checkpoint use one additional transaction, so an acknowledgment failure cannot duplicate tasks. Inline execution retains its existing atomic boundary.
- SecureNow creates a pending admission in the same SQL transaction as Azure snapshot materialization. The current full or incremental choice, subscription and code version are pinned. The prior snapshot reference is selected once and checkpointed before diff. Existing SQL diff persistence supplies a stable pair identity and its consumer checkpoints prevent repeating successful neighborhood work. Carry-forward, path engines, coverage and finding writes, ranking, cut points and routing use the existing scoped output writes and fence independently committed batches. Replays reconcile existing path keys and use a stable observation time. Audit readiness and neighborhood audit are single-attempt consumers, not automatically replayed if their completion is ambiguous. A fallback from failed incremental processing to a different plan is not allowed on a recovered run.
- Capture returns a distinct pending analysis status while the admitted job is waiting. The worker reads pending admissions from active tenant catalogs, then binds the exact workspace/project scope and verifies the stored snapshot before executing. Informational logs and persisted job/stage status distinguish reuse, terminal failure, deadline expiry and handoff. This is not a new customer coverage surface.

## Rollout

Apply tenant migration 439 before enabling recovery. Upgrade all API and worker replicas first. Enable `AnalysisExecution:EnableDurableAuthorityRecovery` and `AnalysisExecution:EnableDurableSecureNowRecovery` independently, starting with an isolated SQL environment. Both default off. `AnalysisExecution:RecoveryMaxAttempts` is clamped to 1–5. For Authority with outbound integration configured, enable the existing transactional integration outbox.

Old runs and stage timeline rows are not backfilled as recovery claims. Keep the migration and active recovery enabled while draining admitted work. Do not downgrade an active worker onto the legacy executor for a partially checkpointed run. The rollback refuses to delete checkpoints or admissions. A deploy with a different engine build refuses to recompute unfinished work against the old input version. Operational replay should start a new analysis rather than clearing the stored evidence.

Cross-run reuse and invalidation belong to FND-076. Customer-facing coverage and conclusion enforcement belong to FND-077.
