# Understanding governance alerts

Governance alerts are created when enabled rules detect findings that require attention. An alert is a follow-up work item driven by alert rules — it is not the same as finding severity. Alerts appear in the Alerts inbox, where authorized users can acknowledge, assign, waive, or resolve them.

## How alerts work {#how-alerts-work}

1. A review identifies architecture findings.
2. Enabled alert rules evaluate those findings.
3. Matching conditions create or update an alert.
4. The alert is routed to the appropriate owner.

## What can trigger an alert {#what-can-trigger-an-alert}

- Severity thresholds on open findings
- Compliance gaps against expected controls
- Policy violations from active governance packs
- Drift or repeated findings across reviews
- Rules that combine multiple conditions

## Where alerts are managed {#where-alerts-are-managed}

Use the **Alerts inbox** to review, acknowledge, assign, waive, and resolve active alerts.

Use **Alert rules** to create thresholds, routing, combined conditions, and simulations.

## Resolving an alert {#resolving-an-alert}

1. Filter or open an alert.
2. Review the linked finding and evidence.
3. Assign an owner or record the appropriate action.
4. Acknowledge, waive, or resolve the alert.
5. Refresh or reevaluate when necessary.

## Related governance concepts {#related-governance-concepts}

**Policy packs** define the governance expectations applied during reviews.

**Standards and rules** show which requirements were evaluated for a review.

**Alerts** surface findings that need attention or follow-up.
