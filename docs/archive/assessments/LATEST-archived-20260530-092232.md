# ArchLucid Assessment – (A) Headline Readiness: 74.33%

This is a clean-slate, first-principles assessment of the current materials available in the repository. The `74.33%` score is the `(A)` headline readiness score per `Assessment-Scope-V1_1.mdc`, excluding items explicitly deferred to V1.1, V2, owner-only commercial action, or `(B)` procurement / market-motion realism.

**Rescore date:** 2026-05-30 — after engineering batch completion for improvements **#1–#24** (excluding deferred **#25–#26**). Prior headline: **71.78%** (archived under `docs/archive/assessments/` when present).

Scoring formula: total weight is `119`; weighted readiness is `sum(score * weight) / 119`. Weighted deficiency signal is `(100 - score) * weight`, and urgency is ranked by that signal rather than raw score alone.

## Executive Summary

### (A) Overall Headline Readiness

ArchLucid is credible for controlled V1 pilots that follow the documented path: configure SQL/auth, create a review, execute agents, commit a manifest, inspect artifacts, and produce a sponsor-safe proof packet. The core product is not vaporware: API contracts, SQL persistence, audit trails, proof packet mechanics, ROI surfaces, config linting, CI gates, tenant-scope guards, retrieval IR harnesses, and an operator decision surface are now materially stronger. The readiness ceiling is pulled down mainly by production-like AI proof breadth, IaC parity gaps for hosted Azure AI/Search/Key Vault, remaining GitHub-link help debt in a few UI surfaces, and Wave **1+** design-system rollout (Wave **0** primitives landed).

### (B) Procurement / Market-Motion Realism

Enterprise procurement friction remains material but is not included in `(A)`. SOC 2 CPA attestation, third-party pen-test publication, named reference customers, live marketplace commerce, and owner-produced demo cohorts are explicitly deferred or informational. The current posture is honest and usable for early diligence: self-assessment, trust center, DPA/SIG/CAIQ-style materials, owner-conducted testing narrative, and procurement pack tooling exist. A rigid enterprise buyer that requires issued SOC 2 or an external pen-test summary will still slow or block procurement.

### Commercial Picture

The commercial story is strong when sold as a service-led, proof-backed architecture review. Pricing, quote request flow, proof packet generation, ROI labels, sponsor summaries, and safe-claim guardrails create a real path to paid pilots. The monetization risk is repeatability: too much revenue still depends on careful operator execution, sales interpretation, and correctly labeled evidence instead of a low-touch purchase-and-expand loop.

### Enterprise Picture

The enterprise architecture is serious: tenant database topology, audit event catalog, RBAC, OIDC/SAML/SCIM posture, governance workflows, policy packs, configuration diagnostics, and trust documents are all present. The gaps are buyer-operational: Wave **1+** UI polish remains, hosted Terraform still lacks full Azure OpenAI/Search/Key Vault private-endpoint parity, and procurement-support artifacts still need owner-defined support/SLA terms (**#25**, deferred).

### Engineering Picture

The engineering base is broad and modular, with many focused tests and contract controls. It is also complex. The highest engineering risks are AI correctness under recurring real LLM execution, retrieval quality at Azure Search scale, remaining IaC parity for hosted Azure dependencies, and proof density under unattended enterprise rollout. Tenant-scope enforcement, snapshot IDOR guards, proxy scope hardening, audit drift gates, and run-detail decision fields are substantially improved but still require operational validation in customer environments.

## Top 12 Most Important Weaknesses

1. Real-mode AI correctness is not yet proven broadly enough across recurring full-pipeline evidence.
2. Retrieval IR harness exists, but production Azure Search scale/parity proof remains thinner than in-memory evaluation.
3. Hosted Terraform still lacks full Azure OpenAI, Azure AI Search, and Key Vault private-endpoint/RBAC composition (**#10–#11** partial).
4. First-pilot success still requires expert choices across SQL, auth, evidence, LLM mode, retrieval, proof, and caveats — chooser/preflight help improved but not eliminated.
5. Wave **1+** enterprise UI design-system rollout (first-pilot path, run detail polish, Home, governance) is not complete — Wave **0** primitives only.
6. ROI proof can still diverge if stale/demo-derived sources shape executive interpretation without careful proof disposition review.
7. Some contextual help and `doc-index.json` entries still link to GitHub blob URLs instead of `/help/{topic}`.
8. Procurement materials are honest but still fall short for rigid buyers demanding formal attestations or exact support/SLA terms (**#25**, deferred).
9. Live self-serve commerce remains deferred (**#26**, owner/commercial un-hold).
10. The codebase is modular but large enough that compatibility stubs and multiple read shapes increase maintenance risk.
11. Production availability evidence and contractual SLO posture remain pre-contract.
12. Optional live LLM CI gates still trade flake risk for assurance density.

## Top 6 Monetization Blockers

1. Proof-to-purchase is still too operator-mediated; a buyer needs guidance to interpret proof status, ROI basis, and next commercial action.
2. Live self-serve commerce / marketplace transactability is deferred, so V1 revenue depends on sales-led quote-to-cash.
3. ROI claims are not yet mechanically impossible to overstate when demo-derived, stale, or unsupported source rows appear.
4. Quote request follow-up and aging need stronger SLA/reporting loops to prevent interested buyers from going cold.
5. The first compelling demo/proof experience is real but still scattered across proof packets, docs, CLI, and UI surfaces.
6. Procurement friction from missing formal attestations can still stall enterprise deals even though it does not reduce `(A)`.

## Top 6 Enterprise Adoption Blockers

1. Tenant-scope and identity-binding backlog items are too important to leave open before broad enterprise rollout.
2. Production-like deployments still depend on IaC gaps for Key Vault, Azure OpenAI, Azure AI Search, diagnostics, ACR, and related services.
3. Operator UI decision screens hide or under-surface failure, governance, retrieval, cost, trust, and disposition signals.
4. Customer self-sufficiency is limited by GitHub-heavy documentation and high setup/interpretation burden.
5. Procurement packages need stricter freshness, placeholder, audit, and policy-pack evidence controls.
6. Support/SLA terms are not yet owner-defined enough for buyers who require contractual operating commitments.

## Top 6 Engineering Risks

1. Cross-tenant data exposure through incomplete scope binding, snapshot reads, retrieval index/query paths, or UI proxy headers.
2. Real LLM outputs passing as sponsor-safe despite weak grounding, missing evidence refs, or low faithfulness.
3. Retrieval silently degrading because there is no stable IR regression harness.
4. Azure production drift because key services and private access controls are not all represented in Terraform.
5. Run approval/commit decisions made without surfaced failure, governance, or finding coverage context.
6. Migration/backfill/idempotency defects causing duplicate, stale, or inconsistent run/proof data under retry.

## Most Important Truth

ArchLucid is good enough for guided, proof-backed pilots, and materially stronger on tenant isolation, operator decision visibility, proof/governance guardrails, and in-app help than the prior assessment. It is not yet good enough for broad, low-touch enterprise rollout without recurring real-mode AI proof, hosted IaC parity (**#10–#11**), and Wave **1+** UI polish.

## Top Improvement Opportunities

### 1. Azure Search Production Client With Tenant Filters

**Why it matters:** Production-like retrieval requires Azure AI Search, but correctness and security depend on every search/delete being tenant/workspace/project scoped.

**Expected impact:** Directly improves Security, Cutting-Edge AI Technology, Correctness, Trustworthiness, and Azure Compatibility.

**Status:** Actionable now.

**Cursor prompt:** Implement the production Azure AI Search retrieval client with tenant-scoped filtering. Start from `ArchLucid.Retrieval`, `AzureSearchTenantScopeFilterBuilder`, `RetrievalIndexingScopeValidator`, and `ArchLucid.Host.Composition/Startup/ServiceCollectionExtensions.AgentsGovernanceRetrieval.cs`. Wire `AzureSearchSdkClient` when `Retrieval:VectorIndex=AzureSearch` and `Retrieval:AzureSearch:Endpoint` is configured. Ensure every query and delete path applies the scope filter derived from `ScopeContext`; platform corpus documents may use only the documented platform sentinel path. Add focused tests in `ArchLucid.Retrieval.Tests` proving tenant, workspace, and project isolation, platform corpus behavior, and failure when Azure Search is selected but endpoint/index configuration is missing. Acceptance criteria: production-like config registers the real client, all search/delete calls include tenant scope, tests cover positive and negative scope cases, and no in-memory retrieval behavior changes for Development/tests. Constraints: do not add MCP or new public routes; do not relax production-like Azure Search lint.

**Impact of running prompt:** Directly improves Security (+6-9 pts), Cutting-Edge AI Technology (+4-6 pts), Correctness (+3-5 pts), Azure Compatibility (+3-5 pts). Weighted readiness impact: +0.5-0.8%.

### 2. Scope-to-Identity Binding at API Ingress

**Why it matters:** Tenant scope must be derived from authenticated identity, not trusted client headers, especially in API key and development-bypass paths.

**Expected impact:** Reduces the highest enterprise security adoption risk.

**Status:** Actionable now.

**Cursor prompt:** Harden API ingress scope resolution so `tenantId`, `workspaceId`, and `projectId` cannot be selected solely by client-controlled headers in production-like modes. Inspect `ArchLucid.Api` authentication/scope middleware, `IScopeContextProvider`, API key auth, development bypass, and tests under `ArchLucid.Api.Tests/Security`. Implement a reconciliation policy: authenticated claims/configured tenant bindings win; mismatched client scope headers produce a safe 403/Problem+JSON; development bypass remains explicit and test-only. Add integration tests for API key, JWT, and dev bypass behavior, including rejected cross-tenant header attempts. Acceptance criteria: production-like modes reject header/identity mismatch, existing local developer flows remain documented, and error bodies include correlation IDs. Constraints: do not change route shapes, OpenAPI DTOs, or tenant database topology.

**Impact of running prompt:** Directly improves Security (+8-12 pts), Trustworthiness (+3-5 pts), Compliance Readiness (+2-3 pts). Weighted readiness impact: +0.4-0.7%.

### 3. Scoped Snapshot Repository Reads

**Why it matters:** Snapshot and child reads by ID alone create IDOR risk in SingleCatalog/dev-like paths and make tenant isolation harder to prove.

**Expected impact:** Closes a concrete data-isolation and correctness class.

**Status:** Actionable now.

**Cursor prompt:** Audit and harden findings, graph, context, provenance, and manifest snapshot read paths so repository methods require `ScopeContext` or tenant/workspace/project filters for externally reachable reads. Start with `ArchLucid.Persistence`, `ArchLucid.Application/Runs`, `IRunDetailQueryService`, and existing scoped snapshot tests. Replace unsafe `GetByIdAsync(Guid)` calls in API/application read paths with scoped variants. Add regression tests for cross-tenant snapshot IDs returning not found/forbidden without leaking existence. Acceptance criteria: externally reachable snapshot reads are scope-bound, tests cover findings/graph/context child loads, and internal migration/backfill code uses explicit internal bypass only where documented. Constraints: do not break in-memory contract tests; do not introduce new database files outside the canonical DDL/migration pattern.

**Impact of running prompt:** Directly improves Security (+7-10 pts), Data Consistency (+3-5 pts), Correctness (+2-4 pts). Weighted readiness impact: +0.4-0.6%.
