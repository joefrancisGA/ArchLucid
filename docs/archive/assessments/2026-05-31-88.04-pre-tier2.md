## 5. Top 8 Most Important Weaknesses

1. **GTM proof density lags product breadth.** The product has strong mechanics (multi-agent, manifests, ROI, governance, explainability) but no self-served proof packet that lets an evaluator reproduce a defensible architecture review output without founder involvement. This is the primary commercial velocity constraint.

2. **Recurring review workflow is not shipped.** Compare, replay, and drift tracking exist but the monitored-risk / findings-digest cadence that converts a one-off review into a repeating value loop is backlog (TB-057–063). Without it, stickiness depends entirely on manual re-engagement.

3. **Onboarding has too many decision branches.** Enterprise implementers face ambiguous choices across auth (Entra/OIDC/SAML/API key), storage (topology mode), execution mode (simulator/real), and retrieval provider (in-memory/Azure Search) before they can produce their first review. This is the primary adoption friction constraint after V1.

4. **IaC WARN rows remain for optional services.** Redis, Cosmos DB, and Service Bus lack Terraform coverage in `infra/terraform/prod` (based on parity scan logic). These are WARN (not HOLD since not pilot-essential), but an enterprise InfoSec audit of the IaC state will surface them as partially out-of-band services.

5. **Dependency graph layering violations (TB-027–032).** Documented architectural debt in the project reference graph. Non-blocking for pilot but increases maintainability drift pressure as the surface area continues to grow.

6. **Support model is founder-operated.** No documented escalation SLA, incident communication template, or named on-call rotation beyond runbook references. Larger enterprise buyers will require evidence that support works without heroic founder involvement.

7. **Documentation drift risk under surface area pressure.** The system is now large enough that a new route, new agent type, or new configuration option can appear in code without updating the audit matrix, route-tier-policy-nav matrix, configuration reference, or trust center. CI guards exist but cover only declared anchor points.

8. **Real AI production scale not demonstrated.** The quad-agent pipeline is tested with credentialed real-LLM validation, but production-scale performance, cost, and reliability evidence under sustained concurrent load does not exist. This is `(B)` procurement friction for enterprise buyers evaluating at fleet scale.

## 6. Top 6 Monetization Blockers

1. **No durable self-served proof that the AI conclusions are defensible.** Decision explainability now exposes the rule audit and coordinator trace, which is strong, but an evaluator still needs a founder to interpret what the policy pack decided and why. A starter proof packet (sample request → sample manifest → explainability walkthrough) would materially reduce this friction.

2. **Self-serve commerce is intentionally parked.** No live Stripe keys, no published Marketplace SaaS offer. Every deal requires quote-to-cash and direct founder involvement. This is owner-gated (V1.1) and does not reduce `(A)`, but it caps revenue throughput.

3. **Recurring review activation is missing.** Without a recurring review cadence, customers have no mechanism for the product to re-engage them automatically. Every return visit is founder-initiated. This limits expansion revenue.

4. **Configuration complexity slows trial-to-paid conversion.** An evaluator who encounters four decision branches before their first review output will often defer or disengage. Reducing these to "try the hosted path first" dramatically shortens the trial cycle.

5. **Self-attested procurement posture creates enterprise deal friction.** The trust center is honest about self-attested SOC 2 and owner-conducted pen test. This is correct behavior, but rigid procurement teams will add review cycles. This is `(B)` informational and does not reduce `(A)`.

6. **No activated "schedule next review" user journey.** The product has the compare and replay surfaces, but there is no CTA on a committed run detail that says "plan the next review." Buyers who don't know to come back won't.

## 7. Top 5 Enterprise Adoption Blockers

1. **Onboarding decision-branch ambiguity (actual V1 blocker for self-directed rollout).** Auth mode, storage topology, execution mode, and retrieval provider present four independent configuration axes. A guided "enterprise preset" that resolves all four for the most common pattern (Entra ID + SystemWithPerTenantCatalogs + real + AzureSearch) would reduce implementation friction to a single decision.

2. **IaC parity WARN rows.** Redis, Cosmos, and Service Bus lack Terraform coverage in the authoritative `infra/terraform/prod` root. An InfoSec team auditing the deployment state will find partially out-of-band services. Not a pilot blocker, but a V1 GA credibility constraint for IaC-first enterprise buyers.

3. **Support model is founder-operated without SLA evidence.** Enterprise procurement requires documented support tiers, escalation paths, and incident communication commitments. These are described at a high level but not demonstrated.

4. **SOC 2 CPA attestation deferred.** Honest about it in the trust center, correctly excluded from `(A)`, but a tangible `(B)` friction item for most Fortune-500 procurement teams. Narrating the roadmap and self-attestation posture is the right approach; expect deal-cycle friction regardless.

5. **No documented V1→V1.1 tenant migration guide.** Enterprise operators who run a V1 pilot want to know how database migrations, API contract changes, and configuration additions will be managed for V1.1. This guide is explicitly V1.1 scoped per `V1_DEFERRED.md` and not a V1 defect, but it creates planning uncertainty for pilot operators.
