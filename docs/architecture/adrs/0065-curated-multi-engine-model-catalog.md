# ADR 0065: Multi-engine model catalog — informed choice, evidence attached, capability enforced

- **Status:** Accepted
- **Date:** 2026-08-07
- **Deciders:** Owner
- **Supersedes:** [ADR 0060](0060-ai-model-chooser-provider-scope.md) **D1 only**. ADR 0060 **D2, D5, D6, D7** remain operative and are restated below; **D3** (TB-872) and **D4** (TB-873) are re-sequenced.
- **Superseded by:** *(none)*
- **Related:** [ADR 0020](0020-azure-primary-platform-permanent.md), [ADR 0005](0005-llm-completion-pipeline.md), [ADR 0056](0056-manifest-online-fine-tuning-governance.md), [`TECH_BACKLOG.md`](../../library/TECH_BACKLOG.md) (**TB-872**, **TB-873**, **TB-2103**–**TB-2109**)

## Context

[ADR 0060](0060-ai-model-chooser-provider-scope.md) **D1** fixed Azure OpenAI as the sole ArchLucid-managed completion provider for V1.x and left the `LlmProviderType` scaffolds for Anthropic, Gemini, and Ollama dormant. It named three reassessment triggers for D1: tenant count ≥ 20, a signed enterprise deal contractually requiring a non-OpenAI provider, or $/review cost pressure the Economy tier cannot meet.

**No D1 trigger has fired.** Tenant count and review volume remain at pilot scale, no signed deal requires a specific non-OpenAI vendor, and the Economy tier is meeting cost targets. This ADR reopens D1 anyway, as an explicit **owner strategic bet** (2026-08-07): the frontier-model field is re-ordering faster than ADR 0060's reassessment cadence assumed, single-vendor capability risk is now judged higher than the N-adapter maintenance cost, and engine choice has become a table-stakes expectation rather than a differentiator. Recording the absence of a fired trigger is deliberate — a future reader must be able to see that this was a judgment call, not evidence-forced.

The ADR 0060 concurrent constraint *"the platform is still producing frequent runtime errors; only the registry/governance/UI slice may proceed near-term"* is resolved as of 2026-08-07 (owner), which unblocks AI-runtime work beyond the governance slice.

**What already shipped** and is reused rather than rebuilt: the provider-neutral seam (`IAgentCompletionClient` / `ILlmProvider`), the `TB-193` factory scaffold (`DefaultLlmProviderFactory`, `LlmProviderType`), tiered routing (`AgentModelTierOptions`, `TieredAgentCompletionRouter`), execution profiles (Economy / Balanced / High assurance), the alias and capability registry (**TB-869**–**TB-871**), per-call provenance (`AgentExecutionTrace` with `ModelDeploymentName`, `ModelAlias`, prompt hash) and run-level `Runs.EngineProvenanceJson`, cost estimation with per-deployment USD rates, the resilience decorator chain (circuit breaking, caching, context-length guard, content safety, accounting), and the faithfulness harness (**TB-683**, `eval_agent_faithfulness.py`) plus the semantic and insight-density judges.

**What is missing** and is the actual scope of this ADR: the alias registry is three entries hard-coded in a C# constructor (`ConfigAgentModelAliasRegistry`), so curation requires a code change and a deploy; there is no way to tell a user what an engine's measured quality is at the point of choosing it; structured-output capability is an all-or-nothing host toggle (`UseJsonSchemaResponseFormat`) rather than a per-engine property; replay comparison does not diff engine identity; and token counting is a single `chars / 4` heuristic that does not hold across tokenizers.

**Alternatives considered:**

1. **Keep D1; ship only TB-872 (BYO Azure OpenAI) and an editable catalog.** Lowest risk and lowest cost. Rejected: it satisfies the cost-control ask but not the capability-risk ask, and leaves ArchLucid's output quality bound to one vendor's roadmap.
2. **Curated catalog where an engine must pass an evaluation gate before it is selectable at all.** Rejected by owner (2026-08-07) after being drafted as the decision: a gate that blocks *offering* an engine until an eval run completes forfeits exactly the reactive speed that motivates this ADR, and "curated" degrades in practice into "whatever the single operator found time to evaluate," which serves the user worse than an honest open list. It also hides the quality judgment inside catalog decisions the customer cannot inspect.
3. **Open catalog with no quality signal and no capability enforcement.** Rejected: an engine that cannot emit the required structured output produces failed runs and silent schema-remediation churn rather than a worse review, and an unlabelled catalog gives the buyer no way to reason about advisory quality.
4. **Open catalog, evaluation evidence attached to each entry and recorded in run provenance, fail-closed only on capability and data boundary — the decision below.** Preserves user autonomy and reactive speed while keeping the evidence story honest: the record says which engine was used and what was measured about it, rather than implying every offered engine was blessed.

## Decision

1. **D1′ — Provider scope reopened.** ArchLucid-managed completion providers are **no longer restricted to Azure OpenAI**. Engines are added as catalog entries (D2′) and are selectable once they satisfy the two fail-closed conditions in D4′ (capability) and D11 (data boundary). Measured quality does **not** gate availability — see D3′. `LlmProviderType` activation happens per engine, in `DefaultLlmProviderFactory`, never by configuration alone, so adding an engine is still a reviewed code change rather than a config edit.
2. **D2′ — Operator-maintained catalog replaces the config registry** (**TB-2103**). The alias and capability registry becomes DB-backed (single DDL file per repo convention) and editable by a platform operator through an internal-only admin surface, with every mutation written to `IAuditService`. Catalog rows carry provider type, engine identity, capability tags, offered task types, structured-output capability level, tokenizer profile, USD rates, data-boundary classification, attached evaluation evidence (D3′), and lifecycle status (`Available` → `Deprecated` → `Retired`). Evaluation state is an **independent** per-task-type field (`Evaluated` / `NotEvaluated`), not a lifecycle stage — an `Available` engine may be `NotEvaluated`. ADR 0060 **D2** is affirmed and unchanged in substance: tenant-facing selection stays **alias- and profile-based**; literal deployment or model names are never exposed in prompts, policies, tenant UI, or tenant API responses.
3. **D3′ — Evaluation evidence is attached, not gating** (**TB-2105**). Where an engine × task type has been evaluated, the catalog row carries the artifact: structured-output conformance rate against the `AgentResult` schema, faithfulness-harness result against the established golden-case floors (**TB-683**), `AgentOutputLlmSemanticJudge` and `PremiumInsightDensityLlmJudge` scores, the delta against the incumbent Standard engine, harness version, and evaluation date. Where it has not been evaluated, the row says so explicitly. **Selection is never refused on measured quality.** The evidence is surfaced wherever an engine is chosen and is recorded, as measured at time of use, in the run's provenance (D5′). Rationale: users are competent to trade quality for cost or speed when told what they are trading, a gate would delay offering a new model until an eval run completes, and a signed review record reading "engine X, conformance 94%, not evaluated for Critic" is more honest than one that offers only pre-blessed options and thereby implies a guarantee.
4. **D4′ — Structured output is a fail-closed capability ladder** (**TB-2104**). Each catalog row declares one of `StrictJsonSchema`, `JsonObject`, or `DegradedTextParse`. Each task declares a **minimum required** level. Routing refuses an engine below a task's minimum rather than degrading silently. `AzureOpenAI:UseJsonSchemaResponseFormat` is retained as the Azure host default but stops being the global determinant. This is the **only quality-adjacent fail-closed control, and it is not a quality judgment**: an engine below a task's minimum does not produce a worse review, it produces failed parses and silent `SchemaRemediationAgentCompletionClientAdapter` churn that surfaces as a cost and latency regression nobody attributes correctly. Refusing it is declining to offer something broken, not protecting a user from a choice.
5. **D5′ — Engine identity becomes first-class run provenance** (**TB-2106**). The engine, catalog alias, capability level, and resolved execution profile are recorded per call on `AgentExecutionTrace` and aggregated into `Runs.EngineProvenanceJson`, which is already commit-frozen by `CommittedRunHeaderAnchorRegistry`. `EndToEndReplayComparisonService` **must** diff engine identity and surface an engine change as the leading interpretation for output drift. Engine identity is deliberately **excluded from `ManifestHash`**: `ManifestHashService` canonicalizes structural manifest sections, commit-freezing already delivers immutability, and adding a field to the hash payload changes hashes for all new commits while buying no property that the anchor trigger does not already provide.
6. **D6′ — Per-engine tokenizer and cost profiles** (**TB-2107**). `CharHeuristicTokenCounter`'s `chars / 4` estimate is retained only for engines whose catalog row declares it acceptable; other engines supply a tokenizer profile or an explicit documented error margin. Pre-flight budget gating (`ArchitectureIntelligenceReviewTierBudgetGuard`) and `LlmCostEstimator` read rates from the catalog row rather than from a deployment-keyed options dictionary.
7. **D7′ — BYO paths are re-sequenced ahead of new managed vendors.** ADR 0060 **D3** (**TB-872**, customer-provided Azure OpenAI) ships **first**, because it builds the per-tenant connection entity, Key Vault credential boundary, per-tenant client resolution, and connection-scoped health and circuit-breaking that every later engine reuses. ADR 0060 **D4** (**TB-873**, generic OpenAI-compatible adapter) ships **second** and is **promoted from V2 to the V1.1/V2 boundary**. Its ADR 0060 gates are re-expressed rather than carried verbatim: the **capability probe remains a hard gate** (D4′), while the **per-alias eval requirement becomes attached evidence** (D3′) — a customer-hosted endpoint that satisfies the capability probe may be used before anyone has evaluated its output quality, with that absence stated on the catalog row and in run provenance. A first non-Azure ArchLucid-managed engine (**TB-2108**) ships **third**.
8. **D8 — Embeddings remain ArchLucid-managed on Azure OpenAI.** ADR 0060 **D5** is affirmed **without change**. Retrieval indices are bound to the current embedding model; BYO or multi-vendor embeddings would force a re-embedding migration with no offsetting benefit. "Customer-selectable engine" therefore covers **completions only**, and buyer-facing copy must say so plainly.
9. **D9 — Metering always; enforcement only where ArchLucid pays.** ADR 0060 **D6** is affirmed. Token usage, cost estimate, and provenance are recorded on **every** execution regardless of engine or payer. Wallet settlement and dollar-budget enforcement apply only to ArchLucid-managed connections; customer-provided connections get visibility and optional workspace quotas.
10. **D10 — Deterministic authority is unchanged on every engine path.** ADR 0060 **D7** is affirmed and is the reason this ADR is safe to accept. Authorization, tenant isolation, evidence identifiers, citation linkage, finalization state, audit history, policy-gate calculation, scoring, retention and deletion, export completeness, and billing enforcement remain ordinary ArchLucid code. Content safety continues to run as a decorator (`ContentSafetyEnforcingAgentCompletionClient`) and therefore applies to every engine without per-engine work. **Engine selection can never alter an authoritative record or a governance outcome.**
11. **D11 — Data-boundary honesty precedes availability** (**TB-2109**). An engine whose endpoint sits outside the ArchLucid Azure boundary cannot be **offered** until the subprocessor disclosure, trust-center entry, and buyer security packet are updated, and a workspace-administrator acknowledgment for regulated evidence is recorded in the audit trail before first use. This remains fail-closed and is **not** overridable by user choice: a customer may consent to their own evidence reaching a third party, but no user can make ArchLucid's published subprocessor list and trust-center statements accurate. The gate binds **ArchLucid's documentation**, not the customer's preference. Documentation is a merge gate, not a follow-up.
12. **D12 — No silent cross-engine failover.** `FallbackAgentCompletionClient` may fail over only within the same engine and provider family. An engine failure never silently reroutes to a different engine, because that would make a run's provenance unreproducible, nor from a customer-provided connection to ArchLucid-paid capacity unless the workspace explicitly opts in.
13. **D13 — Two-tier selection authority.** A **workspace administrator** sets the workspace's **allowed engine set** and its **default**; an **individual user** chooses freely **within that allowed set**, per review, at run creation. Unrestricted per-user choice across the whole catalog is rejected: cross-run comparability is a product promise, and if every reviewer picks independently then `EndToEndReplayComparisonService` diffs are dominated by engine noise and "why does my finding count differ from my colleague's on the same architecture" becomes unanswerable. The allowed set therefore bounds *variance within a workspace* while leaving the quality/cost trade to the person making it. Per-run selection is recorded in provenance (D5′) alongside the resolved execution profile.

## Trade-offs

**Gains.** Single-vendor capability risk drops from total to partitioned: if one vendor's quality or pricing moves adversely, the catalog can be re-pointed per task type without touching agent handlers. Attaching evidence instead of gating on it keeps the reactive speed that motivates the ADR — a newly launched model can be offered the day it appears, labelled `NotEvaluated`, and evaluated afterwards — while still giving the buyer something falsifiable: the signed review record names the engine and what was measured about it at time of use. That is a *more* defensible claim than a curated list, because a curated list implies a guarantee about engines the operator may simply not have gotten to. Two-tier authority (D13) keeps workspace-level comparability intact while leaving the cost/quality trade with the person making it. Because ADR 0060 D7 (now D10) already isolates authority from inference, the blast radius of a poor engine choice is bounded to advisory content quality and never reaches governance outcomes.

**Gives up.** Real cost, paid upfront and recurring: N adapters to maintain, N structured-output dialects to track, and a catalog that is now operational state someone must maintain rather than code someone reviews. The decisive trade is that **advisory quality becomes variable by user choice**. Support and sales must be able to answer "why is this review weaker than the last one" with provenance rather than prevention, and some users will pick a cheap engine, get a thinner review, and read that as a product defect — the mitigation is that the run record can always answer the question, not that the situation is prevented. Unevaluated engines will be used in practice, so `NotEvaluated` must be visible enough to be a real signal rather than fine print, and if it is ignored the honesty of the evidence story degrades to a disclaimer. Prompts tuned against one model family will underperform on others until re-tuned, which will read as an incomplete feature on early non-Azure engines. Keeping embeddings Azure-managed (D8) means the story stays partial and must be worded carefully. Tokenizer divergence makes budget pre-flight less precise cross-engine, so guard thresholds get looser or per-engine, both of which add configuration surface. Most importantly, this is a bet placed **without a fired ADR 0060 trigger**: if capability convergence continues and one vendor stays sufficient, this spend will have bought optionality that was never exercised.

## Constraints

- **[ADR 0020](0020-azure-primary-platform-permanent.md)** — Azure remains primary and permanent for **hosting**. Engines are outbound HTTPS calls from Container Apps; this ADR must not become a multi-cloud hosting posture, and no engine may require workload relocation.
- **Secret boundary** — customer and engine credentials enter only through `ISecretProvider` / `IIntegrationSecretWriter` (Key Vault in production; environment variables in dev). Databases and ordinary configuration store **secret names only**, matching the existing ITSM and Teams pattern and its `NOT LIKE '%://%'` check constraints. No plaintext key columns.
- **JSON-schema structured output is load-bearing** across agent code paths and cannot be weakened globally to accommodate a weaker engine; D4′ exists precisely so weakness is expressed per engine and fails closed.
- **Embedding index binding** — the vector store is tied to the current Azure OpenAI embedding deployment. Re-embedding is out of scope and unfunded.
- **Pilot economics** — pilot-scale tenancy funds neither per-vendor eval corpora at scale nor a re-embedding migration; eval corpora reuse existing golden cases and judges rather than new datasets.
- **Procurement and trust-center claims** — the buyer security packet and subprocessor list are published artifacts. Any engine outside the Azure boundary changes them, and D11 makes that a merge gate rather than a cleanup task.
- **Assurance-claim discipline** — nothing in this ADR may be described as CPA-attested SOC 2 or third-party-pen-tested; those remain owner-execution GTM items.
- **Single operator** — catalog maintenance, evaluation runs, and engine deprecation all land on one person. This is precisely why D3′ does not gate: a gate operated by one person becomes the bottleneck on every model launch. The corresponding risk is that evidence goes stale or is never gathered, so `NotEvaluated` and evaluation age must be first-class in the UI rather than inferred from a missing field.
- **Cross-run comparability** — the product sells comparison across reviews (`EndToEndReplayComparisonService`, decision register, executive rollups). Unbounded per-user engine choice would make within-workspace comparisons dominated by engine variance, which is why D13 bounds the choice set at workspace level rather than removing it.

## Expected impact

**System.** New components are a catalog table plus repository, a catalog-backed `IAgentModelAliasRegistry` replacing `ConfigAgentModelAliasRegistry`, a capability-negotiation step in routing, per-engine adapters behind `ILlmProviderFactory`, an evaluation-evidence store, and workspace allowed-set plus per-run selection plumbing. Falsifiable: no `if (provider == …)` branch appears outside an adapter or the factory; `ConfigAgentModelAliasRegistry` is deleted rather than left alongside the new registry; every live execution records catalog alias plus engine identity on `AgentExecutionTrace`; `EndToEndReplayComparisonService` reports an engine-identity field whenever two runs used different engines; and a run using a `NotEvaluated` engine records that state in provenance rather than omitting it.

**Security posture.** Attack surface grows by one outbound HTTP client shape per engine plus per-tenant credential storage for BYO. Credentials never leave the Key Vault boundary, and the regulated-evidence acknowledgment creates an auditable consent record. Content safety continues to apply on every path via the existing decorator, so no engine bypasses output filtering regardless of who selected it. Falsifiable: a repository test proves no plaintext credential column exists; a routing test proves an engine below a task's minimum capability level is refused; and an authorization test proves a non-admin user cannot select an engine outside the workspace allowed set (D13).

**Operations.** Health probes and circuit breaking extend per engine and per connection; a failing engine degrades only the workspaces selecting it. The predicted decay path shifts with this revision: it is no longer stale `Approved` rows but **evidence that is never gathered**, leaving a catalog of `NotEvaluated` engines where the label stops carrying information. Catalog rows therefore carry evaluation date and the internal surface must make staleness and absence visible. Support gains a new question class — "why was this review weaker" — answerable only from provenance, so engine identity must be visible on run detail, not just in the trace table.

**Cost.** ArchLucid-managed spend is unchanged until a non-Azure engine is actually enabled; BYO shifts token spend to customers and lowers COGS per enterprise tenant, observable in the wallet and usage-MTD ledgers. Evaluation spend becomes **discretionary rather than mandatory** since it no longer gates availability, which lowers the recurring floor relative to a gated design but makes under-investment the likely failure mode. Engineering cost still rises materially and permanently through adapter and dialect maintenance.

**Teams.** Near-term work needs no new vendor SDK expertise: TB-2103–TB-2107 and TB-872 are all catalog, governance, provenance, and per-tenant-connection work on the existing Azure adapter. Vendor SDK knowledge is required only at TB-2108. Sales and support carry new load from D3′ — they must be able to explain variable advisory quality using the run record.

## Consequences

- **Positive:** engine choice becomes a user-facing capability with honest labelling rather than an operator-curated shortlist; single-vendor capability risk is partitioned per task type; a new model can be offered the day it launches; the catalog removes a deploy from every curation change; the evidence story strengthens because the record states what was measured instead of implying a blanket blessing.
- **Negative:** advisory quality becomes variable by user choice, and explaining that is a permanent support and sales cost; `NotEvaluated` engines will be used, so the honesty of the labelling depends on UI prominence that is easy to erode; permanent increase in adapter and dialect maintenance; partial story while embeddings stay Azure-managed; a bet made without a fired ADR 0060 trigger, and therefore the decision most likely to look premature in hindsight.
- **Follow-ups:** **TB-2103** (operator-maintained catalog + internal surface + workspace allowed set), **TB-2104** (fail-closed capability ladder), **TB-2105** (evaluation evidence attached and surfaced), **TB-2106** (engine provenance + replay diff + per-run selection), **TB-2107** (tokenizer and cost profiles), **TB-2109** (subprocessor disclosure + acknowledgment), then **TB-872** (BYO Azure OpenAI), **TB-873** (OpenAI-compatible adapter — capability probe retained as a gate, eval requirement relaxed to evidence), and **TB-2108** (first non-Azure managed engine). **Supersession triggers for this ADR:** (a) if after two non-Azure engines no task type shows a non-Azure engine preferred over the Azure incumbent, a new ADR should retire the multi-engine surface; or (b) if measured quality dispersion across selected engines produces a sustained rise in disputed or withdrawn reviews, a new ADR should revisit whether D3′ should become a gate after all.
